# Honest with / without comparisons

A comparison should reveal what the skill changes, not reward a deliberately weakened control.

1. Fix the brief: rules, levels or random seed, target device, controls, feature completeness and runtime requirements. Keep the baseline competent and playable.
2. For a fresh baseline, use a clean context that has not read this skill or the skill version's art brief. Give it the same functional brief and comparable effort/resources. Record approximate production effort, generated-asset calls, and external assets for each version. If isolation or equal effort is not possible, disclose that limitation instead of claiming a controlled experiment.
3. Share rules and data when useful; keep presentation implementations separate. A boolean that removes illustration, animation or spacing from the skill build is not an independently produced baseline.
4. Freeze the baseline before comparing. Do not degrade it to widen the gap or retrofit it to imitate the skill build. Fix functional bugs in both.
5. Show the same level/seed, state and viewport, with separate launch links. Show an ordinary action as well as a still. Label each version plainly outside the player's HUD.
6. Explain concrete differences and costs: composition, actor silhouette, input feedback, art consistency, readability. Do not present taste as measured fact or a single pair as proof of general superiority.

For iterative skill development, record what the new instructions caused the implementer to do differently. Reading the file, adding a badge, or using a tool is not evidence that the skill improved the result.

Use the same acceptance run on each edition. Where state is deterministic, compare the underlying result after each input. Film the actual surfaces at equal scale and normal speed. Check the image and both public play links after publishing. Keep project-specific levels, edition names and capture code in the showcase, outside the installed skill.
