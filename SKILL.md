# Indie Game Art

Start with the moment the player touches the game. What do they notice, what do they expect to happen, and how does the world answer them? Make visual decisions that bring those three things together.

## Choose the scale of the assignment

| Request | Deliverable |
| --- | --- |
| Polish a button, character scale or animation | Edit it in context. Exercise the states and screens affected. |
| Explore a look before production | Show comparable studies using the same content, camera and display size. Label the stage of work. |
| Redesign a game that feels generic | Diagnose the current build, study relevant examples, establish a visual direction and test it in a playable scene. Carry the result through the requested screens. |
| Finish an agreed direction | Treat approved artwork and interactions as anchors. Complete missing states and transitions. |

## Diagnose the play experience

Inspect the running game when available. Gather the target device, input method, typical viewing size, and the user's latest decisions. Record what they liked with enough precision to preserve it. Approval of a character's ears is useful even when the rest of the character needs work.

Translate criticism into a visible problem and a testable change. “Feels like a website” might mean the instructions get more attention than the board. “Feels AI-generated” might mean every animal has the same silhouette, or the icons each imply a different light source. “Feels lifeless” might mean the room is busy while the object being touched barely responds. Identify the moment and the cost to the player.

## Let references change a decision

Pick examples relevant to the core action, camera, information density or target device. Give each reference one job. Record what you observed, your interpretation, the change you will try, and the properties specific to the source game. Distinguish a screenshot observation from a developer's account or a measured interaction. If a video is unavailable, use the available evidence and identify the gap. See [research and direction](references/research-and-direction.md).

## Define the visual language

Connect the desired feeling to a specific interaction and visible response. In a quiet game of pursuit, the waiting character might barely breathe, a nearby threat might cast a localized glow, and discovery might earn the strongest movement in the scene.

Agree on silhouette, relative scale, camera, edge treatment, light, value hierarchy, material, icon geometry and type at display size. Specify how these choices change between an object's resting and active states. For a broader redesign, adapt the [visual contract](assets/visual-contract.md). Keep only the fields that guide decisions.

## Build one representative moment

Choose a small loop that exposes the hard parts of the direction. A grid game might need a covered tile, an actor, an input, an empty reveal and a discovery. A restaurant game might need an order on a rail, a cook taking it, and the ticket leaving the rail. Use the real background, camera, control surface and target scale.

For an art-only request, deliver the agreed study. For an implementation request, play the loop, correct it and extend the successful choices through the rest of the requested work. Where the user has delegated design decisions, choose a direction and record why. Match the tool to the observed production or rendering need.

## Carry the direction through the game

Use [visual production](references/visual-production.md) for character families, tiles, scenery, generated art and integration. Use [interface and motion](references/ui-and-motion.md) for controls, onboarding, HUD and scene transitions. Keep editable numbers, text and hit areas in the runtime. Share character identities and lighting across screens while giving the lobby, play session and result screen a pace suited to their purpose.

Where available, imagegen, create-game-assets, game-ui-design, game-feel and sprite-animation can help with specialist work. Check their installed instructions and actual capabilities before use. Follow the user's scope and existing authorization for generation, purchases and release.

## Review in play

For each iteration, record the observation, hypothesis, edit and outcome. Compare the same scene under the same conditions. Address recognition and interaction first, then surfaces and small accents. Exercise quick repeats, interruptions, success, failure and relevant player viewpoints. Hidden information, timers, focus and hit targets must remain accurate throughout a transition.

Use [review and iteration](references/review-and-iteration.md) to select checks proportional to the change. Deliver the actual study, production assets, running build or verified release requested. Name the devices and states you exercised and any remaining uncertainty. The [cat-and-mouse case notes](references/session-lessons.md) illustrate how feedback changed one game and which decisions belong to that project.
